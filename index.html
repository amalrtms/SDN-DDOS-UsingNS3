01 · System design

Architecture & design

One controller class drives the whole pipeline — real OpenFlow 1.3 on a topology built so that a port number is, by construction, a source identity.

Point-to-point, not shared, links

Every host — client, attacker, or server — has its own dedicated CSMA link into the switch. There is no shared Ethernet segment, which means a per-port rate is, in this topology, a per-source rate — the property that makes plain port-statistics polling sufficient for detection.

A deliberately slow victim link

The server's own access link is the slowest in the topology (10 Mbps default vs. 100 Mbps for everyone else), modeling the actual resource a volumetric flood exhausts: the victim's own bandwidth, not the core network.

One controller class, two experiments

SdnController implements L2 learning-switch forwarding, OpenFlow monitoring, threshold detection, and DROP-rule mitigation in one place. An EnableMitigation attribute toggles mitigation off per run, so the exact same class drives both the "attack, no mitigation" and "attack, mitigated" experiments.

Real OpenFlow, not a simulation of a simulation

The switch is a real OFSwitch13Device backed by the BOFUSS OpenFlow 1.3 datapath library — actual OFPMP_PORT_STATS multipart messages and actual flow-mod drop rules, not a scripted stand-in for them.

02 · Mechanism

How detection & mitigation work

No machine learning, no statistics beyond a single comparison — a hard project requirement, not a simplification chosen for convenience.

Detection

1
Monitoring

Every MonitorInterval seconds (default 1s), RequestPortStats sends a real OpenFlow port-statistics request (OFPMP_PORT_STATS) to the switch. ProcessPortStatsReply computes (current − previous) / interval for packets/sec per port, logging every sample to monitor-stats.csv.

2
Source identification

Because every host sits on its own dedicated switch port, a port number is a source identity here. The controller also keeps a MAC-learning table (shared with L2 forwarding) to log a human-readable MAC alongside the port.

3
Threshold comparison

CheckThreshold runs the entire detection rule, every time a rate is computed:

bool isSuspicious = packetsPerSec > m_pktRateThreshold;
Packet-in counts are deliberately not used: once a flow is learned and cached, matching packets stop reaching the controller — the entire point of a flow table. An ongoing flood becomes invisible to packet-in counting after its first packet. Port statistics, kept by the switch datapath itself, see it regardless.

Mitigation

1
Install the DROP rule

When a port transitions to suspicious, InstallMitigation sends a real OpenFlow flow-mod:

flow-mod cmd=add,table=0,prio=200 in_port=<port>
2
Why it blocks

No action/instruction clause at all — OpenFlow 1.3 defines an empty instruction set as a silent drop. Priority 200 sits above the learned forwarding flows (100) and the table-miss entry (0), so this rule matches first, before the bottleneck link to the server.

3
Recovery

If the rate later drops under the threshold, RemoveMitigation deletes the rule, restoring normal forwarding:

flow-mod cmd=del,table=0 in_port=<port>
Verified result (Experiment 2 vs. 3): legitimate client packet loss goes from 46.9% (unmitigated) to 5.2% (mitigated) against the identical attack. The server's own received-packet rate, checked directly from its pcap, returns to the exact pre-attack baseline (~366 pkt/s) within one polling interval of mitigation kicking in.

04 · Extension · review feedback

v2: per-source detection & surgical mitigation

The original controller worked, but bluntly: it blocked a whole switch port, which also cut off any innocent host sharing that port with an attacker. A second controller, SdnControllerAdv, fixes that — nothing from Phase 1–13 above was removed or changed to build it.

Think of the controller as a security guard at a door. v1 locked the whole door the moment it saw trouble. v2 checks IDs: it lets good traffic through and stops only the one troublemaker — even when the troublemaker shares a door with someone innocent.

1 · Per-source, not per-port

v1 measured traffic per switch port; two hosts sharing a port were indistinguishable. v2 polls OpenFlow flow-stats and aggregates by eth_src, so it can single out exactly which host is flooding even on a shared line.

2 · Two clues, not one

A flood isn't just lots of packets — it's lots of tiny packets. v2 only raises the alarm when the rate is high and the average packet size is suspiciously small (attacker ≈110 bytes vs. real traffic ≈558 bytes).

3 · A learned baseline, not a guess

There is no universal "X pkt/s = DDoS" standard — v1's fixed 1000 pkt/s was arbitrary. v2 watches the first few quiet seconds, learns the real normal rate (≈123 pkt/s here), and sets the alarm relative to that (≈615 pkt/s) — how production anomaly detectors actually work.

4 · Two-stage, surgical mitigation

On detection the controller first drops the whole in_port (fast but crude), then ≈0.5s later swaps it for a precise ip_src DROP and reopens the port — so an innocent host sharing that port comes right back online.

5 · Repeat offenders get punished

First offense: 5s isolation. Offend again: 20s. A third time: permanently BLACKLISTED. v1 let a paused attacker straight back in the instant its rate dropped — v2 remembers.

6 · A 2nd signal beyond any single source's rate

Flow rate alone misses an attacker who splits a flood across many devices, each individually under the threshold — the real-world case behind Microsoft's 3.47 Tbps / ≈10,000-source Azure attack in Nov 2021. Every poll now also compares the aggregate rate across all sources to a learned aggregate baseline; if it's anomalously high and entropy stays high (many roughly-equal contributors, not one dominant flood), a time-limited DISTRIBUTED_ALERT temporarily tightens every source's own threshold, so each contributing device trips the existing per-source detector on the next poll.

How the advanced controller stops the flood

Learn a baseline. The first ~7s of quiet traffic set the normal per-source rate (≈123 pps); the alarm threshold is set relative to it, not hard-coded.
Poll by source. Every 1s, flow-stats are summed by eth_src — so port 9's two hosts are measured separately even though they share a line.
Detect on two signals. A source trips the alarm only when its rate beats the adaptive threshold and its packets are small — port 9's attacker hits ≈39,062 pps at ≈110 bytes/pkt and trips at t≈11.0s, port 9's innocent host does not.
Mitigate, then isolate, then penalize. prio 200 in_port=9 → DROP goes in immediately; ≈0.5s later it's replaced by prio 210 ip_src=10.1.1.9 → DROP and the port reopens — the innocent host on port 9 is back online within half a second, while the attacker's own block gets 5s → 20s → permanent across repeat offenses.

Theory

Other ways to detect a DDoS — and which v2 uses

Real detectors rarely rely on one signal; they combine several. v2 moved from a single rate check (v1) toward combining rate, packet size, and an adaptive baseline — the direction the field actually goes.

MethodWhat it looks forTrade-offIn v2?
Rate / volume thresholdToo many packets/bits/flows per secondSimple; false-alarms on legit busy periodsYes
Packet-size / payloadFloods use many tiny, uniform packetsCheap; attackers can pad packets to evadeYes
Entropy (statistical)Randomness of source/destination IPs & ports; a flood collapses entropyStrong, standard in SDN research; needs a windowLogged only
Adaptive baseline / anomalyDeviation from the learned normal (moving average, EWMA, std-dev bands)Adapts per network; needs a clean learning periodYes
Flow-based featuresMany new/short-lived flows, few packets-per-flow, high flows-per-sourceGood for distributed attacks; more state to track—
Source distribution / asymmetryMany sources → one victim; lots of traffic in, little outCatches reflection/amplification; needs topology view—
Protocol / connection behaviorSYN-without-ACK ratio, half-open TCP, odd UDP/ICMP ratiosGreat for SYN floods; protocol-specific—
SDN control-plane signalsSpike in packet-in / table-miss rate / flow-table growthSDN-specific and powerful; easy future add-on here—
Signature-based (IDS)Matches known attack fingerprints (Snort-style rules)Accurate for known attacks; blind to new ones—
Change-point / time-seriesSudden statistical shifts over time (CUSUM, wavelets)Catches abrupt onset; tuning-sensitive—
Machine learningTrained classifier (decision tree, SVM, k-NN, random forest, or unsupervised k-means / isolation forest / autoencoder)Most powerful and flexible; needs training data, heavierDeliberately avoided — project brief
There is no official international standard pps value for a DDoS — the "right" threshold depends entirely on a network's own normal load. The professional approach is baseline-relative / anomaly detection (or ML), not a fixed constant, which is exactly the direction v2 moved in. Documented, not built: rate-limiting with OpenFlow meters instead of an outright drop, plus the remaining signals above (source-distribution, SDN control-plane spikes, a simple ML classifier over the features already logged).
Evidence

Is there research behind the threshold number?

Yes — and every source below reaches the same conclusion v2 is built on: nobody publishes a universal packets/sec constant, because the published work all detects relative to a learned normal (a moving baseline, a standard-deviation band, or entropy), not a fixed number.

SourceWhat it doesHow it relates to v2
Dwi Ary W., Improving DDoS Detection using Entropy in SDN, Telkom University, 2016The classic SDN baseline method: flags traffic above mean + 3 standard deviations of normal volume, with an entropy check added to cut false positives from legitimate bursts.Same shape as v2's BaselineMultiplier × baseline threshold — a statistical deviation from a learned normal, not a constant.
Entropy Based DDoS Detection and Mitigation in OpenFlow Enabled SDNDetects a flood as a collapse in source/destination entropy, then mitigates directly through OpenFlow flow-mods.Confirms entropy as a standard secondary SDN signal — which is exactly why v2 already logs SourceEntropy per poll (see the chart above).
Rényi joint-entropy dynamic threshold, Applied Sciences, 2022Targets SDN control-plane DDoS at both low- and high-rate attack levels using a dynamic, not fixed, threshold.Backs the "no single pps number works across attack intensities" point this section already makes.
When Time Meets Space: Entropy Integration and Dynamic Threshold for Adaptive DDoS Detection in SDN (preprint)Combines spatial + temporal entropy with a second-order EWMA threshold; reports 99.26% recall / 3.2% false-positive rate on a testbed.Shows that combining signals with an adaptive threshold (what v2 does: rate + packet size + baseline) measurably beats a single fixed signal.
The escalating-block-then-blacklist pattern in Penalties above also mirrors a well-established methodology outside academic SDN research: fail2ban's bantime.increment lengthens a repeat offender's ban (often geometrically, capped at a maximum), and its recidive jail permanently bans IPs that keep coming back — the same 5s → 20s → permanent BLACKLISTED shape SdnControllerAdv implements. In both systems, unblocking is strictly time-based (a hold-down timer); it is never triggered just because the offending traffic's rate happens to drop, which is exactly what review feedback asked this project to check.
Scale

Where this sits next to a real attack

This project's attack (≈39,000 pps / ≈20 Mbps per attacker, on a lab topology) is intentionally small enough to run in ns-3 and to reason about by hand. Real recorded attacks are several orders of magnitude larger — the table below keeps that honest.

SourceScaleTechnique used
This project (ddos-advanced)≈39,062 pps / attackerPer-source rate + packet-size + adaptive baseline, two-stage port→IP block
Microsoft Azure, Nov 20213.47 Tbps / 340M ppsFrom ≈10,000 distinct source IPs across 10+ countries — no single source's rate was remarkable
Cloudflare, Aug 202511.5 TbpsAutomated hyper-volumetric UDP-flood auto-mitigation at the network edge
Google / Cloudflare, Oct 2023398M / 201M req/sHTTP/2 "Rapid Reset" — application-layer rate limiting, not just packet rate
The idea under test here — measure a per-source rate against a learned-normal baseline, and escalate the response for repeat offenders — is the same idea production DDoS defenses use, just at a scale where a single attacker is rarely the whole story. The Azure row above is exactly the case per-source detection alone cannot catch: ≈10,000 sources, each individually unremarkable, overwhelming the victim together. That gap is exactly what improvement 6 · a 2nd signal beyond any single source's rate (above) is for: a per-source rate check alone never catches it, which is why an aggregate-rate check now backs it up.
05 · Honesty

Bugs found & known limitations

Two real correctness bugs were found while building traffic monitoring — both confirmed with actual packet captures before being called "fixed," not assumed.

Bug 1 · Forwarding

eth_dst-only flow matching never learned a pure responder's MAC

switch-stats-*.log showed every single data packet hitting the controller via packet-in for the entire run, well past steady state. Cause: flow-mod rules matched only eth_dst = <learned mac>, so a host that only ever replies (the server) never had its own MAC learned — its replies always matched the requester's already-installed flow and were forwarded without ever reaching the controller. Fixed by matching on the (eth_src, eth_dst) pair, the same approach the standard Ryu simple_switch_13 tutorial controller uses.

Bug 2 · Channel modeling

Unrealistic channel delay silently capped every host to ~500 pps

A configured 20 Mbps flood (~39,062 expected pkt/s at 64-byte packets) measured only ~350–430 pkt/s leaving the attacker's NIC — regardless of whether the configured rate was 1 Mbps or 20 Mbps. Cause: every CSMA link used Delay = 2ms (WAN-style latency on what should model a LAN); ns-3's CsmaChannel holds the shared bus for the full propagation delay per transmission, capping acquisitions at 1/0.002 = 500/sec regardless of application rate. Misdiagnosed twice before being found (first suspected switch capacity, then the default FqCoDel queue discipline) — fixed by changing Delay to MicroSeconds(2) on every link; verified the attacker's port then showed ~39,062 pps, matching theory exactly.

  • The detection-threshold sweep (Experiment 5) shows flat results across 200/1000/5000 pkt/s because the tested attack (~39,062 pkt/s) sits far above all three — a real property of that experiment's specific setup, not a bug. A threshold between the legitimate rate (~122 pkt/s) and a weaker attack would be a more sensitive test; the parameters make this easy to run (--attackRate=1.5Mbps --threshold=300, for instance).
  • Mitigation blocks by switch port, not by IP/MAC identity — correct and sufficient for this topology (one host per port), but would need extending (matching on eth_src/ip_src instead of in_port) for a topology where multiple hosts can share a port.
  • Detection latency is bounded below by MonitorInterval (default 1s) — an attack is never caught faster than one polling cycle. Lowering the interval trades CPU/control-channel overhead for faster detection.
